# NETSCOPE — прошивка для Xiaomi BE7000 на базе QWRT

**Русский** | [English](README.en.md)

[![Тесты](https://github.com/lststrdst/qwrt-be7000-wifi7-lab/actions/workflows/tests.yml/badge.svg)](https://github.com/lststrdst/qwrt-be7000-wifi7-lab/actions/workflows/tests.yml)

Я разрабатываю NETSCOPE как самостоятельную прошивку для Xiaomi BE7000
(RC06) на базе QWRT R26.02.02 / QSDK 12.5. Моя цель — сохранить аппаратные
возможности QWRT и собрать вокруг них понятную домашнюю систему: единый
интерфейс, наблюдение за трафиком, безопасный быстрый VPN setup, восстановление
и отдельную лабораторию Wi‑Fi 7/MLO.

NETSCOPE не маскирует происхождение базы: в интерфейсе и документации остаётся
`Based on QWRT`, а оригинальные авторы QWRT сохраняют свои атрибуции. Этот
репозиторий не является официальным проектом QWRT.

> Готового публичного образа для прошивки пока нет. В репозитории находятся
> исходники компонентов, тесты, обезличенные примеры и release gates. Первый
> образ появится только после закрепления воспроизводимой базы сборки,
> установки на запасной слот и проверки восстановления.

## Зачем мне это нужно

BE7000 работает у меня главным домашним шлюзом. Через него идут обычный
интернет, удалённый доступ, IoT, офисный туннель и выборочная маршрутизация.
QWRT даёт нужную низкоуровневую базу, но повседневная эксплуатация требует
более цельного продукта: чтобы состояние сети было видно в одном месте, VPN
не настраивался набором случайных команд, а рискованные изменения нельзя было
случайно закрепить в загрузке.

Я строю прошивку вокруг четырёх правил:

- штатные функции QWRT остаются доступными;
- каждое изменение сети имеет preflight, собственный scope и откат;
- секреты и данные конкретного роутера не попадают в Git;
- экспериментальные функции выключены по умолчанию и не маскируются под stable.

## Что входит в NETSCOPE

| Подсистема | Что делает | Статус |
|---|---|---|
| NETSCOPE Dark | единая английская оболочка LuCI, вход, поиск и версия базы | работает на тестовом роутере, упаковка в образ впереди |
| Traffic / NETSCOPE | устройства, conntrack, направления, порты, объёмы, PCAP-сессии | прототип и runtime-компоненты готовы |
| VPN Quick setup | WG, AWG, VLESS/Xray и Mieru из вебки | черновики и preflight; plain WG имеет отдельный runtime с watchdog |
| Recovery | известное рабочее состояние, бэкапы и порядок возврата | документировано, образ ещё не выпущен |
| IoT monitor | кольцевой журнал Wi‑Fi, WAN и DNS для выбранных устройств | готов как отдельный инструмент |
| Wi‑Fi 7 / MLO Lab | восстановление заводской схемы 5G low + 5G high | только модель и тесты, live apply отсутствует |

Подробная карта компонентов находится в [firmware/README.md](firmware/README.md),
а критерии первого образа — в
[firmware/RELEASE-CHECKLIST.md](firmware/RELEASE-CHECKLIST.md).

## Почему IoT вынесен отдельно

На общей MLO/combined-сети маломощные 2,4‑ГГц устройства периодически теряли
доступ в интернет, хотя сам WAN оставался жив. Это проявлялось у голосовой
колонки и стало причиной для отдельной IoT-сети только на 2,4 ГГц; позже туда
же добавлен пылесос. Основная сеть получает к IoT только нужный локальный
доступ, а сами устройства не участвуют в экспериментах с 5 ГГц/MLO.

Это не попытка объявить MLO неисправным стандартом. Проблема относится к
конкретной комбинации клиентов, band steering и текущей реализации прошивки.
Архитектура и диагностический план описаны в
[docs/IOT-NETWORK.md](docs/IOT-NETWORK.md).

## Wi‑Fi 7 как отдельная экспериментальная функция

Заводская Xiaomi умеет разложить внешнее радио на два 5‑ГГц PHY и объединить
их в MLD. В текущей загрузке QWRT внешний QCN9224 работает в single-PHY режиме.
Для заводской split-схемы нужны согласованные GPIO, BDF, ART offset, параметры
CNSS, конфигурация MLO и корректный порядок запуска драйвера.

Сейчас в репозитории есть две разные модели:

1. Аппаратная транзакция с обязательным UART 1,8 В — для будущей полноценной
   отладки и фиксации результата.
2. Теоретический supervised runtime trial без UART — только после загрузки,
   только в RAM, без UCI commit/autostart/bootenv/MTD и с возвратом после
   холодного включения.

Вторая модель защищает от сохранения неудачного состояния во flash, но не
устраняет электрический риск GPIO и не спасает работающим watchdog при kernel
hang. Поэтому она остаётся **моделью и набором тестов**, а не кнопкой в вебке.
Подробности, известные константы, матрица отказов и критерии успеха собраны в
[docs/WIFI7-MLO.md](docs/WIFI7-MLO.md).

## Проверка модели без UART

```bash
python -m pip install -e .
python -m unittest discover -s tests -v
python -m be7000_wifi7_lab profiles/be7000-rc06-qwrt-r26.02.02.json
python tools/check_public.py
```

Тесты проверяют отказ до мутации при попытке записать постоянное состояние,
откат при ошибке драйвера/PHY/MLD/LAN/WAN, timeout подтверждения, отдельный путь
для kernel hang и возврат к baseline после reboot. Ни модель, ни OpenWrt helper
не содержат live-команд изменения CNSS, GPIO, Wi‑Fi, MTD или U‑Boot.

## Текущая граница безопасности

- Не записывать ART, MIBIB, bootloader, bootenv и разделы NAND.
- Не переносить BDF/caldata с другого экземпляра роутера.
- Не включать MLO из автозагрузки до аппаратной проверки и серии cold boots.
- Не считать Ethernet абсолютным recovery-каналом: при kernel hang он тоже
  исчезнет.
- Не публиковать VPN-ключи, Wi‑Fi пароли, серийные номера, MAC-адреса и backup
  живой конфигурации.
