# VPN Quick setup

Я добавил мастер в LuCI, чтобы базовая подготовка не требовала ручного
редактирования файлов через SSH. В NETSCOPE ссылка находится в верхнем
блоке меню; на обычной теме — Services → VPN Quick setup.
Адрес: `/cgi-bin/luci/admin/services/netscope_setup`.

## Текущий этап

| Вариант | Что создаётся | Что ещё нужно |
|---|---|---|
| WireGuard | Уникальные `server.conf`/`client.conf`; отдельная подтверждаемая активация | Проверка внешней доступности с клиента; autostart намеренно выключен |
| AmneziaWG | Такие же конфиги с согласованными параметрами AWG v1 | Совместимый AWG runtime и отдельная проверка клиента; это не AWG 2/3 |
| VLESS / Xray | `xray.json`, локальный SOCKS на `127.0.0.1:2081` | Запуск, split/full routing, DNS и failover |
| Mieru | `mieru.json`, SOCKS только на loopback, порт 2082 | Сервер, runtime, проверка соединения и включение резерва |

### WireGuard / AmneziaWG

1. Выбрать протокол, указать внешний IP/DDNS и UDP-порт.
2. Мастер предлагает свободный UDP-порт и не пересекающуюся с активными
   маршрутами туннельную подсеть; обе проверки повторяются при подготовке.
   LAN подставляется с текущего устройства;
   офисные маршруты добавляются явно в CIDR. Пересечение с выбранным туннелем отвергается.
3. Нажать **Prepare private configuration** и сохранить оба файла приватно.
4. Для обычного WG выполнить свежий **Run activation preflight**, проверить
   результат и отдельно подтвердить **Activate separate WireGuard**.

Генерация ключей работает установленным `wg` или `awg`, не случайной строкой
из браузера. В клиент не прописывается неработающий DNS и не добавляется
default route. Серверный файл — native setconf, адрес интерфейса указан в
метаданных плана; это не готовый `wg-quick up` файл. Вместе с профилями можно
скачать обезличенный `plan.json`: будущие изменения и пройденные проверки,
без закрытых ключей. Статус WG показывает
существующие интерфейсы: пустой список не означает наличие настроенного сервера.

### Транзакционная активация обычного WireGuard

Активатор создаёт только интерфейс `nswg0` и chains `NS_WG_INPUT`,
`NS_WG_FORWARD`, `NS_WG_NAT`. Он не выполняет `uci commit`, не меняет default
route, не перезапускает network/firewall и не трогает другие VPN. Разрешены
только указанные в клиентском профиле LAN/office CIDR; для них используется
отдельный scoped MASQUERADE, чтобы обратный маршрут не требовался на каждом хосте.

Старт двухфазный. После создания интерфейса и правил runtime остаётся pending;
backend проверяет link, `wg show` и все три jump. Только затем он подтверждает
профиль. Если backend оборвался, watchdog удаляет jumps, chains и интерфейс.
При ручном Stop сначала удаляются traffic-affecting jumps. После reboot профиль
не запускается сам. AWG, Xray и Mieru этим активатором не поддерживаются.

### VLESS / Xray

Вставить **один outbound JSON**, не подписку и не полный config. Поддержаны
TCP/raw, WebSocket, gRPC и XHTTP с TLS/Reality. Проверка сертификата не отключается.
Если Xray установлен, выполняется только `xray run -test -config …`, без
подключения к серверу. Успешная проверка синтаксиса не доказывает доступность VPN.

### Mieru

Без сервера оставить адрес, имя и пароль пустыми — получится `TEMPLATE` с
`server.example.invalid` и `CHANGE_ME`, а не якобы рабочий VPN.
Если сервер уже есть, заполнить все три поля и нужный TCP/UDP-порт.
Формат взят из [документации Mieru](https://github.com/enfein/mieru/blob/main/docs/client-install.md).
Проверка совместимости с установленной версией и автоматический failover
пока не реализованы. Пароль сервера не нужно присылать мне или добавлять в Git.

## Хранение и безопасность

Текущий целевой профиль требует writable USB в `/mnt/sda1`. Файлы сохраняются
в `/mnt/sda1/NETSCOPE/config/setup/<id>/` с правами 0600, каталоги — 0700.
Автоматического переноса на внутреннюю flash при потере USB нет.
Не более 20 сохранённых черновиков; старые нужно приватно архивировать и удалить
администратору. Вебка показывает обезличенный список черновиков. Кнопка preflight
повторно проверяет USB, файлы, runtime, порт, подсеть, forwarding и firewall
capability, но ничего не включает. Удаление требует подтверждения, выполняется
POST+CSRF и отказывается работать при неожиданном файле, symlink или active-marker.
Автоматического удаления чужих настроек нет.

API наследует авторизацию LuCI. Создание — POST с CSRF-токеном, скачивание
только после входа и по whitelist имён; traversal и symlink отвергаются.
Ответ подготовки не содержит ключей/паролей. Скачанные файлы их содержат:
это не обезличенные примеры. Browser storage/analytics не используются.
Через HTTP пользоваться только доверенной LAN/VPN: HTTP не шифрует формы.

Подготовка, просмотр, preflight и удаление не запускают службы и не меняют сеть.
Только отдельная подтверждённая кнопка активации обычного WG создаёт описанные
выше runtime-объекты; UCI/default route остаются неизменными. Мастер не включает
публичный SOCKS и не перехватывает трафик. Если процесс оборвался и остался `setup-lock`,
проверить отсутствие выполняющегося запроса перед удалением только пустого
каталога `/tmp/netscope-setup/setup-lock`; не удалять рабочие черновики вслепую.

## Проверки

На QWRT R26.2.2: 48 проверок backend в приватных временных USB-каталогах,
включая настоящие ключи и Xray `-test`. Тестовые ключи удалены после проверки.
35 браузерных проверок на синтетической странице, 10 lifecycle-проверок
настоящих WireGuard/iptables в disposable network namespace и 28 live LuCI
HTTP/CSRF/download проверок.
Тестовые данные — не пользовательские профили.

Сквозной тест нового профиля с внешнего клиента не выполнялся: для него нужен
реальный endpoint/проброс и ручное включение. AWG/VLESS/Mieru по-прежнему не
активируются этим мастером.
